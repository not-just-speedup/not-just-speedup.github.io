### G9: Precision, and whether the acceptance caught its effect

**Conclusion:** `lower-accepted-within-tolerance`. On the scored instance and 4 other level-1 instances, the line passes run in double-float (2×FP32, ≈48-bit significand), below the FP64 working precision. Their error (1–4e-14) stays at least 10× below the CPU baseline's own deviation, which the acceptance formula's last term admits. The solution is more accurate than the baseline there.

**Precision used:**
- df64 spectral line passes and kernel spectrum: double-float with two-sum/FMA renormalisation (solution.cu:267–329, 729–786, 964–1138). Integer-bit double↔df conversions (:482–530); below 2⁻⁷⁰ or above 2¹⁰⁰ the hi part alone is kept (:485).
- FP64 spectral path: FP64 FFT and operator (solution.cu:148–262, 692–728, 791–962).
- Multipliers G, H, Fs: double-double with binary powering (solution.cu:69–129, 573–615).
- kappa/e1 sums: FP64 FMA accumulation with dd scaling (solution.cu:611–690).
- Twiddles and cos/sin tables: long double on the host (solution.cu:1388–1430).
- Replica: IEEE FP64 with explicit `__dmul_rn/__dadd_rn/__ddiv_rn`, no FMA contraction (solution.cu:1147–1236).
- No fast-math (fixed runner flags), no tensor cores.

**Accuracy:**
- Level 1: all 8 instances pass with 0 mismatches and exact-region equality. `margin` ranges from 9.8e-5 (scored) to 1.8e-3 (speed-gate).
- The agent, against `__float128`/long-double references:
  - FP64 path ≈1e-15; df64 1–4e-14 (S186, S308).
  - Needed factor ≤ 0.0032 on big shapes (S554), ≤ 0.046 mid-size (S324, worst at (151, 585)), ≤ 0.057 in the edge sweep (S592), 0.0005 at n1=6900 (S321); public example 0.0 (S628).
  - Self-check maximum differences against the CPU baseline (e.g. 3.25e-12 at 500×1000, S429) are dominated by the baseline's own error.
- No error was measured by this analysis.

**Acceptance: `lower-accepted-within-tolerance`.** The df64 path is accepted because `factor·max|cpu−ref|` dominates the allowance at those shapes. Without that term, `atol + 4·eps·|ref|` ≈ 1.4e-15 at |ref| ≈ 1 would reject df64-level errors. The solution's error is still 10–1000× below the baseline's, so no accuracy that the baseline has was lost.

**Acceptance-rule notes:**
- (1) The term `factor·max_over_array|cpu − ref|` scales with the baseline's worst element error, which grows with ρ = n1²/n0. The agent measured 1.8e-8 at (10, 4000) (S114) and 2.6e-6 against the CPU at (2, 6800) (S317). At the scored shape the brief's `cpu32_scale` is 1.9e-10, if that is the baseline's maximum deviation. So the rule would accept an accuracy loss of several orders of magnitude relative to FP64 at large ρ. It cannot catch a loss smaller than 4× the baseline's worst error.
- (2) Where the baseline is nearly exact (tiny shapes, heavy decay: cpu_err 1e-20…1e-26, S607), the allowance falls to `atol + 4·eps·|ref|` ≈ 6 ulp at |ref| ≈ 1. Rounding-order differences alone used up to 0.67 of the agent's atol-free factor there (S607, (1, 4)) and 1.72 in a prototype (S59). This is still within the factor of 4, but it is the tightest region of the rule.

### G10: Algorithmic changes, and whether they keep the kernel general

**Conclusion:** General. The kernel is PolyBench/C 4.2.1 `adi` (KERNEL.json): `n0` Peaceman–Rachford ADI steps of the 2-D heat equation on an n1×n1 grid with unit Dirichlet boundaries, from an arbitrary initial `u`. The closed form, the zero-padded convolution and the boundary correction compute exactly that linear map for any finite `u`, any `n0 ≥ 1` and any n1. They rely only on linearity, on coefficients fixed by (n0, n1), and on the fixed boundary value 1, which every instance of this kernel has. No bug on allowed inputs was found by reading.

**Changes:**
1. Closed-form evaluation of all `n0` steps. `W = U − 1`; P_n and Q_n are diagonalised by the DST-I; the n0-th powers are taken per mode in double-double. Code: solution.cu:5–9, 573–690, 1535–1585.
   - General: **yes**. Each step is `W ← P W Q` with P, Q functions of tridiag(−1, 2, −1), whose eigenvectors are discrete sine vectors. The first step's use of the user's boundary columns is kept (rank-2 term; solution.cu:994–1000, 1101–1133).
   - Tests: CPU sweeps against `__float128` (S48–S80); GPU sweeps (G2); level 1, 8/8.
2. Toeplitz-minus-Hankel propagators applied by zero-padded FFT convolution, any 5-smooth M ≥ 2N, two real lines per complex FFT. Code: solution.cu:1283–1316, 964–1138.
   - General: **yes**. Exact linear convolution for every M ≥ 2N; no dependence on the factorisation of n1−1.
   - Tests: S73–S80, the edge sweep with M = 2N and primes (S563–S592).
3. Dispatch to a bit-exact literal replica for n1 ≤ 5 && n0 ≤ 16 and n1 ≥ 6915, and no work for n1 ≤ 2. Code: solution.cu:1617–1634, 1143–1236.
   - General: **yes**. This is the baseline's own algorithm; for n1 ≤ 2 the baseline also does nothing.
   - Tests: S106, S317 (bit-exact at n1=7100), S334–S364.
4. Scratch arrays v, p, q (buf1–buf3) are not materialised.
   - General: **yes**. They are scratch in the contract, and PolyBench's adi dumps only `u`.
5. In the replica, the p/denominator recursion is computed once per call, because it does not depend on the column. Code: solution.cu:1147–1179. General: **yes**, bit-identical.

**Task conditions relied on:**

- **Another stated condition.** The df64 path depends on the acceptance formula's `factor·max|cpu−ref|` term: its ≈1e-14 error exceeds what FP64-level accuracy (`4·eps·|ref|`) allows. To close the gap the contract would have to state a magnitude range for which FP64-level relative accuracy is required.
